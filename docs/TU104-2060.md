# RTX 2060 (TU104) port: status and reproduction plan

This is a **source port only**. No hardware run has been performed on TU104. Read
[SAFETY.md](SAFETY.md) first; nothing in this document authorizes execution.

## Target card observed on this host

- Gigabyte RTX 2060, lspci: `TU104 [GeForce RTX 2060]`, `10de:1e89`,
  subsystem `1458:3fc1`, rev `a1`, 6 GiB GDDR6, BDF `0000:01:00.0`.
- IOMMU group 1 shared with `0000:00:01.0` (root port) and the three sibling
  functions (`01:00.1` audio, `01:00.2` USB, `01:00.3` UCSI). No bus-wide resets.
- Driver at observation time: NVIDIA proprietary `550.163.01`, kernel
  `7.0.12+kali-amd64`. The validated Leadtek experiment ran NVIDIA open
  `595.99.02` on kernel 6.8; post-unlock behavior of the proprietary 550
  driver on Turing is unverified. Prefer reproducing the validated driver
  generation before interpreting results.

## Why this port should transfer

Evidence for family transfer, each with its source:

1. **Register map.** The whole flow uses BAR0 offsets that are identical on the
   two empirically-validated cards: CMP 40HX (TU106, `unlock40x_v70.c`) and the
   2080 Ti (TU102): BOOT0@0, `0x100ce0` usable-FB, PLM `0x409650`,
   SS0/SS1 `0x409664`/`0x40966c`, WPR2 `0x1fa824`/`0x1fa828`, GFW `0x118234`,
   GSP falcon `0x110000`, SEC2 falcon `0x840000`, VBIOS scratch 0e = `0x1438`.
   nouveau maps **all** Turing FB to `tu102_fb` → `gp102_fb_oneinit`, and
   `gp102_fb_vidmem_size()` reads `0x100ce0` with the same
   `lmag << (lsca+20)` (+ ECC 15/16) decode used by the core.
2. **FRTS placement.** FRTS = FB − 2 MiB on both anchors: 22 GiB →
   `0x57fe00000`; 8 GiB (TU106) → `0x1ffe00000`. 6 GiB → `0x17fe00000`.
   WPR2 HI lands at FRTS + 0xe0000 on both.
3. **Firmware heap.** `GSP_FW_HEAP_PARAM_BASE_RM_SIZE_TU10X = 8 MiB`
   ("Turing thru Ada"), `GSP_FW_HEAP_PARAM_SIZE_PER_GB = 96 KiB/GiB`,
   client alloc 96 MiB — `open-gpu-kernel-modules gsp_fw_heap.h` +
   `_kgspCalculateFwHeapSize`. 6 GiB → 8 + 1 + 96 = **105 MiB**.
4. **External blobs.** The same four blobs (`bl_gsp_tu102.bin`,
   `booter_ucode_prod.bin`, `v67_payload.bin`, `gsp_rm_boot_dbg.bin`) served
   both CMP 50HX (TU102) and CMP 40HX (TU106). TU104 reuse is the working
   hypothesis, **not** an established fact.

## What stays per-card (guaranteed to refuse until observed)

- Native FWSEC: parsed from THIS card's own full 1 MiB PROM capture
  (`kernel/tu104_diag.ko` exports it read-only via debugfs when the card is
  unbound). `tools/rom_analyze.py --rom prom.bin --extract local/tu104-fwsec.bin`.
- Pre-driver register tuple: BOOT0, workspace, WPR2 initial, selectors,
  feature/readout/GFW words.
- PCI identity (already inventoried) and target BDF.

## Procedure (offline until the PROM snapshot)

1. `python3 tools/inventory.py --bdf 0000:01:00.0 --output local/inventory.json`
2. Build `kernel/tu104_diag.ko` (`make module` builds it; read
   `kernel/tu104_diag.c` first). Boot a **separate diagnostic initramfs**
   where udev does not bind nvidia to the card, load it with
   `target=0000:01:00.0`, export `/sys/kernel/debug/tu104_diag/prom.bin`,
   and copy the printed offset lines into an observations JSON:
   keys `bdf, device_id, subsystem_vendor, subsystem_device, boot0,
   capacity_register, workspace_register, wpr2_low_init, wpr2_high_init,
   selector0_init, selector1_init, feature_word, readout_word, gfw_word`.
3. `python3 tools/profile_gen.py --rom local/prom.bin --observations local/obs.json \
   --profile-name tu104-2060-6g-reviewed --header kernel/tu104_profile.h \
   --profile-json profiles/tu104-2060-6g.json`
   The tool refuses unknown chips, malformed descriptors, bad layouts.
4. Offline gates: `make test` (now includes the TU104 host suite), then
   `make test-private ASSETS=...` equivalent only applies to the TU102 flow;
   for TU104 review the generated header + `tools/check_assets.py
   --assets ... --profile profiles/tu104-2060-6g.json`.
5. Build with execution opt-in after YOUR OWN review:
   `make module ENABLE_EXPERIMENT=1`, install for the tested kernel only,
   one-shot initramfs gate per [TURING.md](TURING.md) §5, targeting
   `0000:01:00.0`. Never the default entry; never auto-retry.
6. Success criteria and recovery are the same as TURING.md §6: full log
   quadruple, healthy driver bind, then FP16→FP32 vs FP16→FP16 A/B
   throughput plus numerical validation. The 2080 Ti result (59.9 → 111.0
   TFLOPS mmapeak) is the only hardware evidence; RTX 2060 TFLOPS
   expectations remain predictions, not results.

## Known open items

- TU104 FWSEC blob: never published; must come from this card's PROM.
- Blob family reuse on TU104: unvalidated (see caveat above).
- Driver 550 (proprietary) post-unlock binding: unverified.
- The executor pins `0x409650 == 0xffffff8f` (locked PLM) and the observed
  selector tuple; if this card's pre-driver state differs, `profile_gen.py`
  and the guards must be re-derived, never bypassed.
